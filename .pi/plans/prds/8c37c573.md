# Product objective

Deliver a realistic, phased upgrade of the apply patch tool that materially improves correctness and operator trust without rewriting the full system.

# User problem

Users and agents need patch application that is dependable under drift and retries. Current behavior can be difficult to reason about when hunks are ambiguous, errors are under-specified, or partial operations are possible.

# Scope boundaries

In scope:
- Harden unified-diff parse, preflight, and commit flow.
- Improve deterministic matching and ambiguity rejection.
- Strengthen transactional behavior for create/edit/move/delete.
- Add structured result reporting for machine loops.
- Harden strict unified-diff-only input flow with deterministic parse and preflight diagnostics.

Out of scope for this PRD:
- Full AST-semantic patching across languages.
- Comprehensive binary patch support.
- Automatic conflict resolution that chooses among ambiguous matches.
- UX redesign beyond result payload and diagnostics.

# Non-goals

- Replacing unified diff as canonical execution artifact.
- Shipping best-effort silent patching behavior.
- Building language-specific refactor engines.

# Constraints

- The tool MUST fail fast with descriptive typed errors.
- The tool MUST preserve current create/edit/move/delete capability.
- The tool MUST remain transactional (no silent partial writes in strict mode).
- The implementation MUST keep compatibility with existing extension wiring.
- Tests MAY be executed only upon explicit user request.

# Deliverables

1. PRD-approved design for phased hardening of apply patch.
2. Spec updates for parser, matcher, planner, and commit transaction behavior.
3. Structured output contract including per-file and per-hunk statuses.
4. Error taxonomy and payload format.
5. Unified diff parser and healing hardening spec with deterministic behavior guarantees.
6. Rollout plan with default-safe flags and migration notes.

# Testable acceptance criteria

1. Given a valid multi-file unified diff, when run in strict mode, then all hunks apply or none are persisted.
2. Given an ambiguous hunk anchor, when preflight runs, then the tool returns AmbiguousApplyError with candidate locations and performs no writes.
3. Given unsupported optional features (for example binary patch when disabled), when parsing/preflight runs, then the tool fails with UnsupportedFeatureError before commit.
4. Given a retry of an already-applied patch, when idempotence checks run, then the result classifies already_applied without corrupting content.
5. Given create/edit/move/delete operations in one patch, when commit succeeds, then all operations are applied consistently and reported in structured output.
6. Given dry run enabled, when a patch is processed, then no filesystem mutation occurs and a complete plan/result summary is returned.
7. Given malformed unified diff input, when parsing runs in strict mode, then the tool fails with typed `PatchParseError` and performs no writes.
8. Given parse output handoff to preflight, when healing finds non-unique anchors, then the tool fails with explicit ambiguity diagnostics and commit does not start.
