# Context

This spec is REQUIRED context-linked to PRD `8c37c573` (Realistic Apply Patch Upgrade). It focuses on parsing and healing features for the apply patch tool and MUST keep lifecycle user-controlled.

# Technical design

## Design scope

This spec covers:

- patch parsing
- healing strategies for hunk anchoring drift
- deterministic diagnostics from parse and healing phases

This spec does not redefine commit transaction behavior beyond parse and preflight outputs.

## Parsing architecture

The parser MUST implement a two-pass model:

1. lexical pass
2. structural pass

### Lexical pass

The lexical pass MUST tokenize:

- file headers (`diff --git`, `---`, `+++`)
- extended headers (`index`, `rename from`, `rename to`, mode headers)
- hunk headers (`@@ -a,b +c,d @@`)
- hunk body lines (` `, `-`, `+`, EOF marker)

Lexing MUST preserve source line offsets for every token.

### Structural pass

The structural pass MUST build a typed AST:

- patch set
- file patch nodes
- hunk nodes
- line nodes

Structural invariants MUST be validated:

- each file patch has valid old and new markers
- each hunk header count matches line payload shape
- operation kind derivation is deterministic (`create|edit|move|delete`)

Invalid structure MUST fail with `PatchParseError`.

## Healing architecture

Healing is the preflight anchoring subsystem used after successful parse.

Healing MUST attempt anchors in strict order:

1. exact location from hunk header
2. bounded window relocation (`offsetWindow`)
3. full-file exact context scan (if enabled)
4. bounded fuzz (if enabled)

Healing MUST compute candidate scores from:

- context coverage
- distance from expected location
- uniqueness

If top score is non-unique, healing MUST return `AmbiguousApplyError`.

## Idempotence-aware healing

Healing MUST support `already_applied` detection by verifying:

- old sequence is absent at viable anchors
- new sequence already exists with matching context envelope

Idempotence classification MUST be stable for the same baseline and options.

# Constraints

- Parsing MUST be deterministic for identical input bytes.
- Healing MUST NOT mutate filesystem state.
- Ambiguity MUST fail fast in strict mode.
- Unsupported features discovered in parse MUST stop downstream healing.

# Edge cases

1. Multiple `diff --git` headers for same path with non-contiguous hunks.
2. Hunk header counts mismatch actual payload counts.
3. Repeated identical context blocks causing anchor collisions.
4. File renamed and edited with missing `rename from` but changed path markers.
5. EOF newline marker inconsistent with hunk payload.
6. CRLF input patch applied to LF file baseline.
7. Patch includes unsupported binary block while `allowBinary=false`.
8. Patch text containing non-diff wrapper lines that break grammar and MUST be rejected.

Each edge case MUST map to deterministic parse or healing outcomes with typed errors.

# Deterministic verification criteria

1. Given same patch bytes and options, parse AST hash MUST be identical.
2. Given same file baseline and heal options, candidate ordering MUST be identical.
3. Given malformed patch structure, parse MUST fail with `PatchParseError`.
4. Given ambiguous anchors in strict mode, result MUST be `AmbiguousApplyError` and no commit handoff.
5. Given already-applied hunk baseline, healing MUST classify `already_applied` consistently.
6. Given identical baseline and options, healing relocation and fuzz reporting MUST remain stable.
